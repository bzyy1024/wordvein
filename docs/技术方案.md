# 英语词根词缀词典网站 — 需求与技术设计方案

> 版本：v1.0（MVP）
> 目标：**输入单词 → 看词根词缀拆解 → 由词根反查同族词** 的核心闭环
> 部署方式：自有服务器 Docker Compose
> 数据来源：由需求方自行提供，本文档定义数据交换格式，开发方编写导入脚本

---

## 一、项目定位与目标

### 1.1 一句话定义

一个面向中国英语学习者的**词根词缀拆解查询站**：查任意单词能看到它的构词逻辑，并能顺着词根看到一整族同源词。

### 1.2 核心价值

| 用户痛点 | 本站解法 |
|---|---|
| 单词背了就忘，孤立记忆效率低 | 给出构词逻辑：`pre-`+`dict`+`-able` = "预先说出（结果）→ 可预测的" |
| 想知道"哪些词是同一个词根" | 词根页聚合全部同族词，按词频排序，一次记一串 |
| 词缀易混（`-able` / `-ible`、前缀 `in-` 三义） | 词缀页统一说明 + 常见混淆提示 + 例词 |
| 词根有变体（`spect/spec/spic`）导致查不全 | 变体关联，查 `spect` 自动带上 `spic` 系列 |

### 1.3 非目标（MVP 明确不做）

- ❌ 用户系统、登录、生词本、间隔复习（SRS）
- ❌ 单词发音音频、图片、在线测试
- ❌ 移动端 App、小程序
- ❌ 商业化（广告、付费词书）

这些作为二期候选，一期的数据模型已为其预留扩展位，届时加表不加结构改造。

### 3.1 页面清单

| 路由 | 页面 | 渲染策略 | 说明 |
|---|---|---|---|

| `/morpheme/[slug]` | 词素详情（词根/词缀） | SSR | slug 统一命名，如 `/morpheme/dict`、`/morpheme/pre`、`/morpheme/able` |
| `/morphemes` | 词素总览 | ISR（1h） | 筛选：类型 / 来源语言 / 字母序 / 词数 |
| `/search?q=` | 搜索结果 | SSR | 单词区 + 词素区分栏展示 |
| `/about` | 关于与数据来源 | SSG | 说明方法论、数据出处、免责声明 |

### 3.2 外部 API（供后续扩展/第三方调用，MVP 内部可用 Server Component 直查库）

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/search?q=&type=&limit=` | 混合搜索，返回单词与词素两类结果 |
| GET | `/api/words/:word` | 单词详情（含 senses + breakdown + 推荐词） |
| GET | `/api/morphemes/:slug?include_words=1&limit=50` | 词素详情（含变体 + 派生词分页） |

> MVP 阶段页面本身通过 Server Component 直接读库，这几条 API 只是对外/异步交互（如下拉补全）时使用，避免不必要的网络往返。

### 3.3 关键查询

**① 单词拆解**（F3）

```sql
SELECT wm.position, wm.order_no, wm.note,
       m.id, m.form, m.slug, m.type, m.meaning_cn, m.origin_lang
FROM word_morphemes wm
JOIN morphemes m ON m.id = wm.morpheme_id
WHERE wm.word_id = (SELECT id FROM words WHERE lower(word) = lower($1))
ORDER BY wm.order_no;
```

**② 同族词（含变体展开）**（F5 + F7）

```sql
-- 第 1 步：把该词素及其变体 id 汇成一个集合（应用层做，或写成 VIEW）
WITH target(id) AS (
  SELECT id FROM morphemes WHERE slug = $1
  UNION
  SELECT to_id FROM morpheme_relations
  WHERE relation = 'variant' AND from_id = (SELECT id FROM morphemes WHERE slug = $1)
  UNION
  SELECT from_id FROM morpheme_relations
  WHERE relation = 'variant' AND to_id = (SELECT id FROM morphemes WHERE slug = $1)
)
SELECT w.id, w.word, w.phonetic, w.freq_rank, w.cefr,
       m.form AS matched_form, m.slug AS matched_slug,
       (SELECT string_agg(s.definition_cn, '；' ORDER BY s.sort_no)
          FROM senses s WHERE s.word_id = w.id) AS brief
FROM word_morphemes wm
JOIN words w ON w.id = wm.word_id
JOIN morphemes m ON m.id = wm.morpheme_id
WHERE wm.morpheme_id IN (SELECT id FROM target)
  AND ($2::smallint IS NULL OR w.difficulty <= $2)
ORDER BY (m.slug = $1) DESC, w.freq_rank NULLS LAST, w.word
LIMIT $3 OFFSET $4;
```

> `ORDER BY (m.slug = $1) DESC` 保证直接派生排在变体派生前面。

**③ 模糊搜索 + 拼写容错**（F1）

```sql
CREATE EXTENSION IF NOT EXISTS pg_trgm;

SELECT id, word, phonetic, similarity(word, $1) AS sim
FROM words
WHERE word % $1 OR lower(word) LIKE lower($1) || '%'
ORDER BY sim DESC, freq_rank NULLS LAST
LIMIT 20;
```

> `%` 是 pg_trgm 的相似度算子，配合 `gin(word gin_trgm_ops)` 索引，亚毫秒返回。

**④ 中文含义反查**（F1）

```sql
SELECT m.id, m.slug, m.form, m.type, m.meaning_cn
FROM morphemes m
WHERE m.meaning_cn ILIKE '%' || $1 || '%' OR m.etymology ILIKE '%' || $1 || '%'
ORDER BY m.word_count DESC LIMIT 20;
```

## 四、数据库选型（结论先行）

### 4.1 结论

**主存储：PostgreSQL 16**（理由见下）。**不使用图数据库作为主存储。**

### 4.2 为什么是 PostgreSQL 而不是图数据库

你的本质数据关系是"**单词 ←多对多→ 词素 ←多对多→ 单词**"，深度只有 **1~2 跳**，这是教科书级的关系型场景，不是图场景。

| 维度 | PostgreSQL（推荐） | 图数据库（Neo4j / NebulaGraph 等） |
|---|---|---|
| 本次核心查询（同族词） | 一次 JOIN + 索引，亚毫秒 | 同样快，但无优势 |
| 数据规模 | 万级词 × 十万级关系，PG 单机轻松 | 大材小用 |
| 全文/模糊检索 | **pg_trgm 原生支持拼写容错**，无需外挂 ES | 不擅长，需另配搜索引擎 |
| 数组类型 | `variants TEXT[]` 直接存变体，省一张表 | 属性也支持，但生态弱 |
| 递归/多跳 | `WITH RECURSIVE` 足够支撑词源树 | 强项，但本期用不上 |
| 运维成本 | 你已经有了，备份/监控成熟，**零新增组件** | 新增组件、新增备份策略、需额外学习 Cypher/GQL |
| 团队/后续维护 | SQL 通用技能，任何人可接手 | 依赖特定图查询语言，交接成本高 |
| 扩展性 | JSONB 存音标/例句富结构，随时加功能 | 灵活但弱约束，易脏数据 |

**一句话**：图数据库的优势在"多跳路径发现/最短路径/社区发现"，而你要的是"某个词根下有哪些词"——这是一个带过滤和排序的二级索引查询。为了 10% 的场景引入 100% 的运维复杂度，不划算。

**何时再考虑图库**（届时作为 PG 的**只读同步副本**，而非替换）：
- 做跨语言词源演化：PIE 原始印欧元音变换 → 希腊语 → 拉丁语 → 古法语 → 英语，需要可视化多跳路径
- 做"词语相似度图谱"（基于共享词素计算语义关联度）

### 4.3 为什么不是 MySQL（你也有）

MySQL 8 并非不能用，但本项目有 3 个硬伤：

1. **无 trigram 索引**：拼写容错（F1 硬需求）需要额外搭 Elasticsearch 或写 Levenshtein UDF，成本陡增；MySQL 全文索引对 3 字母短单词（`dict`、`able`）有 `ft_min_word_len` 限制且对英文单词搜索效果差。
2. **无数组类型**：变体列表 `variants` 需额外拆表或塞 JSON，查询别扭。
3. **递归 CTE / CTE 优化弱**：二期做词源树会明显吃力。

> **兼容说明**：若你的服务器运维已高度标准化在 MySQL（例如统一备份平台只支持 MySQL），可以做 MySQL 降级版——本文的数据模型全部可平迁（`TEXT[]` 换成关联表，trigram 换成应用层首字符过滤 + Levenshtein 二次排序）。请明确告知，我再出一版 MySQL DDL。

### 4.4 容量估算

| 项 | MVP 预估 | 满负荷预估（10 万词） |
|---|---|---|
| `words` | 5 万行 | 10 万行 |
| `senses` | 12 万行 | 25 万行 |
| `morphemes` | 500~800 行 | 2000 行 |
| `word_morphemes` | 12 万行 | 30 万行 |
| 总体积 | < 100 MB | < 300 MB |

单机 PG 完全无压力，`shared_buffers` 给到 512MB 即可全内存命中索引。

## 五、技术栈

| 层 | 选型 | 理由 |
|---|---|---|
| **Web 框架** | Next.js（App Router）+ TypeScript | **SEO 是本项目的生命线**——<｜hy_place▁holder▁no▁813｜>流量来自"xxx 单词词根"这样的百度/谷歌长尾搜索，必须服务端渲染生成可被爬虫抓取的 HTML。SPA 方案（React + 独立后端）直接淘汰。 |
| **样式** | Tailwind CSS + shadcn/ui | 拆解块、词素卡片等 UI 需要精细控制，shadcn 组件可复制源码、无锁定风险 |
| **图标** | Lucide Icons | 轻量，tree-shaking 友好 |
| **ORM** | Drizzle ORM（`drizzle-orm` + `node-postgres`） | Schema 用 TS 描述，类型端到端安全；迁移文件可读可 review；比 Prisma 更轻、冷启动更快 |
| **数据库** | PostgreSQL 16（+ `pg_trgm` 扩展） | 见第四章论证 |
| **运行时/包管理** | Node.js 24 LTS + pnpm | 构建快、磁盘占用小，容器内安装快 |
| **容器化** | Docker + Docker Compose | 见第七章 |
| **反向代理** | Nginx（HTTPS 终结 + gzip/brotli + 静态资源缓存） | 你的服务器已有 Nginx 可复用，只需加一个 server 块 |
| **CI/CD** | GitHub Actions 构建镜像 → 服务器 `docker compose pull && up -d` | 零停机替换容器 |
| **数据导入** | 独立 TS 脚本 `scripts/import.ts`（CLI） | 幂等 upsert，输出校验报告 |

> **为什么不用 Python/Java 后端 + React SPA**：SPA 首屏 HTML 是空壳，百度抓不到词根内容，等于放弃自然流量。若你有强烈的后端语言偏好（如 Java/Spring Boot），可改为"Spring Boot 提供 API + 独立的 React SSR 方案（如 Remix）"，但复杂度上升，不推荐。

## 六、数据库 Schema

完整 DDL 见 [`docs/schema.sql`](./schema.sql)，核心表如下（均已在上文 ER 逻辑中验证）：

```
words ──┬─< senses                    -- 单词与其义项/例句
        ├─< word_morphemes >── morphemes   -- 拆解关联（核心多对多）
        └─< word_tags >── tags        -- 考试标签/主题标签
              morphemes ──< morpheme_relations（变体/同源/反义，指向自身）
```

**关键表说明**

| 表 | 作用 | 设计要点 |
|---|---|---|
| `words` | 主词表 | `word` 唯一索引；额外建 `lower(word)` 唯一索引防重复入库；`freq_rank` 用于同族词默认排序 |
| `senses` | 义项 | 一词义项分离，`pos` 可为 `null`（无词性数据） |
| `morphemes` | **词素表（核心资产）** | `form` 存规范写法（`pre-`、`-able`、`dict`），`slug` 存 URL 友好形式（`pre`、`able`、`dict`）；`type` ∈ `root/prefix/suffix/stem/combining`；`variants TEXT[]` 存异体；`word_count` 冗余计数由导入脚本回填，用于排序和总览页展示热度 |
| `word_morphemes` | **拆解关联表（核心）** | `order_no` 决定拼接顺序；`position` 标槽位（前缀/词根/后缀）用于配色；`note` 存"在这词里它具体什么意思"（如 `dict` 在 `verdict` 里是"说"，但在 `diction` 里也是"说"，note 可写"说话方式→措辞"） |
| `morpheme_relations` | 词素间关系 | `relation` ∈ `variant`（变体，如 dict/dic）/ `related`（相关）/ `opposite`（反义前缀，如 pre-/post-）/ `derived`（派生） |
| `tags` / `word_tags` | 标签 | 预留给二期的考试词单（四级/考研/雅思） |

## 七、Docker 部署架构

```
                   Internet
                      │
                 ┌────▼─────┐
                 │  Nginx   │  HTTPS 终结 / gzip / 静态资源缓存 / 反代
                 │ (已有)   │
                 └────┬─────┘
                      │ http://localhost:3000
        ┌─────────────▼─────────────┐
        │   Docker Compose Stack    │
        │  ┌─────────────────────┐  │
        │  │ web                 │  │
        │  │ Next.js  standalone │  │
        │  └──────────┬──────────┘  │
        └─────────────┼─────────────┘
                      │ DATABASE_URL（外部实例）
        ┌─────────────▼─────────────┐
        │  PostgreSQL 16 + pg_trgm  │  外部实例，不在 compose 中部署
        └───────────────────────────┘
```

**要点**

- 只部署 `web` 一个服务，数据库直连外部实例，compose 里没有 `db` 容器，也就没有数据卷要维护。
- `web` 镜像使用 Next.js `output: 'standalone'`，产物镜像约 250MB，不含 devDependencies。
- **数据库凭据只在 `.env` 中维护一份**（`DATABASE_URL`），由 `docker-compose.yml` 注入容器；用 `:?` 强制校验，漏配时直接报错而不是带空串启动。
- 建表 / 建扩展由宿主机脚本 `pnpm db:init` 执行（`docker/postgres/01-init.sql` + `docs/schema.sql`，幂等），不依赖 initdb 挂载。
- **数据导入不走容器内的运行时**：由 `scripts/import.mjs` 直连外部库执行，保证导入逻辑可版本化管理。

## 八、数据来源：导入规范

你已有自己的词表/数据源，开发方**不负责生产数据内容**，只负责**定义格式 + 编写导入脚本 + 输出质量校验报告**。

格式规范详见 [`docs/数据格式规范.md`](./数据格式规范.md)，简而言之：

- 提供 **2 个 JSONL 文件**（每行一个独立 JSON 对象，便于增量追加、便于逐行校验）：
  1. `morphemes.jsonl` — 词素（词根/词缀）定义
  2. `words.jsonl` — 单词、释义、例句、拆解引用
- 不需要你手工生成 `word_morphemes` / `morpheme_relations` 表的内容，导入脚本根据 `breakdown` 与 `variants` **自动生成**。
- 导入脚本会产出 `data/import-report.md`，列出：入库成功数、**未定义词素**（单词引用了但 `morphemes.jsonl` 里没有的 form）、无拆解词数量、重复词、字段缺失明细 —— 便于你补齐数据。

## 十、风险与对策

| 风险 | 影响 | 对策 |
